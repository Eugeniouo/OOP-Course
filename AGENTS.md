# Правила работы агента в этом репозитории

Краткий ориентир по проекту курса ООП (C++20). Цель — один репозиторий на весь
семестр: Lab 1 закладывает данные и предобработку, следующие работы наращивают
тот же код.

## Структура

```text
OOP_Labs/
├── CMakeLists.txt      # корневая сборка
├── include/            # публичные заголовки библиотеки ядра
├── src/                # реализация библиотеки
├── apps/               # консольные приложения (Lab 1 CLI и далее)
├── tests/              # тесты под CTest
├── data/               # датасеты локально, в Git не коммитить
├── docs/
│   ├── dataset.md      # описание выбранного набора
│   ├── agent_log/      # журнал эпизодов работы с агентом
│   └── labs_description/  # условия и методички (не код)
├── AGENTS.md
└── README.md
```

Логика данных и преобразований — в библиотеке; ввод/вывод для пользователя — в
`apps/`. Условия лабораторных лежат в `docs/labs_description/`, исходники туда
не кладём.

## Сборка и проверки

- C++20, CMake ≥ 3.24.
- Сборка без предупреждений при `-Wall -Wextra`.
- В Debug подключены AddressSanitizer и UndefinedBehaviorSanitizer; тесты
  должны проходить с ними.
- Тесты регистрируются в CTest; падение — ненулевой код возврата.
- Предпочитаемая последовательность после правок: configure → build → ctest.

Команды сборки и запуска фиксируются в README проекта; если их ещё нет —
сначала предложи варианты под текущий `CMakeLists.txt`, затем правь код.

## Стиль C++20

Ориентиры, которые уже заложены в курс и удобны в этом проекте:

- пропуски — `std::optional`;
- столбец числовой или категориальный — `std::variant` (или эквивалент с тем же
  смыслом);
- вычислительные функции по числам — `std::span<const double>` (или аналог);
- стратегии обработки — `enum class`, не строки и не «магические» числа;
- пути — `std::filesystem`;
- владение через RAII / стандартные контейнеры и умные указатели;
- алгоритмы и ranges там, где это упрощает код без лишней магии.

Пиши код так, чтобы его можно было объяснить на защите: ясный инвариант класса,
понятные имена, без скрытых глобальных состояний.

## Датасет

Рабочий набор: **Productivity Prediction of Garment Employees** (UCI).
Подробности — в `docs/dataset.md`. Кратко для кода загрузчика:

- файл: `data/garments_worker_productivity.csv`;
- разделитель `,`, строка заголовка есть;
- пропуск — **пустое поле** (в CSV видно как `,,`), сейчас это столбец `wip`;
- отклик: `actual_productivity` (регрессия);
- `date` не включать в числовую матрицу признаков для моделей;
- `team` по смыслу категориальный (номера команд 1…12);
- при загрузке нормализовать `department`: `sweing` → `sewing`, обрезать
  пробелы (`finishing ` → `finishing`).

Специфика формата (разделитель, маркер пропуска, нормализация) держится в
конфиге загрузчика, а не размазывается литералами по всему коду. Имена столбцов
и их число определяются из файла.

## Git

- Несколько осмысленных коммитов вместо одного «всё сразу» в конце работы.
- Сообщение коммита описывает изменение по сути.
- В репозиторий не попадают: каталог сборки, `data/`, бинарные артефакты,
  секреты.
- История должна отражать ход работы над лабораторной.

## Журнал агента

Файл текущей работы: `docs/agent_log/lab_N.md` (для первой — `lab_1.md`).

Записывай **эпизод**, только если он повлиял на проект (архитектура, датасет,
CMake, нетривиальный фрагмент кода, разбор ошибки, текст README).

Шаблон эпизода:

1. **Запрос** — суть промпта своими словами или короткой цитатой;
2. **Что получили** — идея / код / совет;
3. **Что приняли / изменили / отклонили и почему**;
4. **Как проверили** — сборка, тест, просмотр файла, ручной запуск.

Не нужно логировать весь диалог подряд и мелкие уточнения без следа в
репозитории. Журнал оценивается по содержательности, не по объёму.
