# Датасет

## Какой набор используем

В проекте используется набор
[Productivity Prediction of Garment Employees](https://archive.ics.uci.edu/dataset/597/productivity+prediction+of+garment+employees)
из UCI Machine Learning Repository
(DOI: [10.24432/C51S6D](https://doi.org/10.24432/C51S6D)).

Это данные о ежедневной работе команд швейной фабрики: сколько людей в смене,
сколько было сверхурочных, какой стоял план по производительности и какой
результат получился по факту.

Локальная копия файла лежит в `data/garments_worker_productivity.csv` и
**не коммитится** в Git (каталог `data/` в `.gitignore`).

| Параметр | Значение |
|---|---|
| Объектов (строк) | 1197 |
| Столбцов | 15 (14 признаков + отклик) |
| Разделитель | запятая `,` |
| Строка заголовка | есть |
| Обозначение пропуска | пустое поле между запятыми (в CSV это выглядит как `,,`) |
| Задача | регрессия: предсказать `actual_productivity` |

Выбор датасета не окончательный: при необходимости набор можно заменить позже,
если он окажется неудобным. Требования к данным те же, а замена фиксируется в
этом разделе README.

---

## Что предсказываем

Отклик — столбец **`actual_productivity`**: фактическая производительность
команды за день, число от 0 до 1.

В следующих лабораторных это будет задача **регрессии** (предсказать число).
При желании из того же столбца можно сделать классификацию, разрезав значения
на классы (например, «ниже плана / около плана / выше плана»), но базовый
сценарий курса для этого набора — регрессия.

## Признаки

Ниже — смысл столбцов и то, как программа их трактует после загрузки.

### Категориальные

| Столбец | Смысл | Заметки |
|---|---|---|
| `quarter` | Часть месяца (`Quarter1` … `Quarter5`) | `Quarter5` — дни 29–31; таких строк мало (44) |
| `department` | Цех | В сырых данных есть опечатки и лишние пробелы (см. ниже) |
| `day` | День недели | Строки вроде `Monday`, `Thursday` |
| `team` | Номер команды (1…12) | В файле записан цифрами, но по смыслу это **идентификатор команды**, а не измерение. Программа считает его категориальным (мало уникальных значений) |

### Числовые

| Столбец | Смысл |
|---|---|
| `targeted_productivity` | Целевая производительность на день (план) |
| `smv` | Standard Minute Value — нормативное время на операцию |
| `wip` | Work in progress — незавершённые изделия |
| `over_time` | Сверхурочные, минуты |
| `incentive` | Денежная премия (BDT) |
| `idle_time` | Время простоя производства |
| `idle_men` | Число работников в простое |
| `no_of_style_change` | Сколько раз меняли стиль изделия |
| `no_of_workers` | Число работников в команде |

### Служебный столбец (не признак для модели)

| Столбец | Решение |
|---|---|
| `date` | Дата записи (`M/D/YYYY`). Для статистики её можно показать, но в предобработанную числовую матрицу для моделей **не включаем**: это метка времени, а не измеряемый признак объекта. |

## Пропуски

Пропуски есть **только в столбце `wip`**: 506 пустых значений из 1197
(~42%).

В исходном CSV пропуск — это **пустое поле**, а не строка `NA` или `?`.
При загрузке пустое поле превращается в отсутствующее значение
(`std::nullopt`), а не в ноль и не в «магическое» число.

Важный нюанс по смыслу: пустые `wip` почти целиком относятся к цеху
finishing, а у sewing значения обычно заполнены. То есть пропуск здесь часто
связан с тем, как вели учёт в разных цехах, а не с «случайной дыркой» в данных.
Для лабораторной это всё равно обычный missing value: в статистике он не
участвует, а при предобработке числовые пропуски заполняются выбранной
стратегией (по умолчанию — медианой по уже посчитанной статистике).

## Нюансы сырых данных, о которых стоит знать сразу

### 1. Опечатки в `department`

В файле встречаются три «разных» значения:

- `sweing` — опечатка, имеется в виду sewing (швейный цех), 691 строка;
- `finishing` — без пробела, 249 строк;
- `finishing ` — с пробелом в конце, 257 строк.

Для человека это два цеха, для программы без очистки — три разные категории.
В загрузчике значения нормализуются:

- `sweing` → `sewing`;
- обрезка пробелов по краям → `finishing` сливается в одну категорию.

Так статистика и one-hot кодирование отражают реальные цеха, а не артефакты
набора.

### 2. `team` записан числами

Столбец выглядит как числовой, но значения — только номера команд 1…12.
Складывать «команду 3» и «команду 5» бессмысленно, поэтому тип определяется
как **категориальный** (мало уникальных значений среди чисел).

### 3. `Quarter5`

Пятая «четверть» месяца — это хвост календаря (29–31 числа), таких наблюдений
мало. Мы оставляем категорию как есть: это часть исходных данных, а не ошибка
формата.

### 4. Файл заточен под этот датасет, но без хардкода схемы

Программа знает специфику набора через **конфиг загрузчика** (разделитель,
признак пропуска, наличие заголовка, нормализация `department`, исключение
`date` из матрицы признаков). Имена и число столбцов из файла не зашиты
константами: добавление столбца или изменение порядка не ломает загрузку.

## Как это стыкуется с лабораторной

1. CSV читается → столбцы получают типы (числовой / категориальный).
2. Считается сводка и статистика **по исходным данным**, до заполнения
   пропусков.
3. По запросу выполняется предобработка: заполнение пропусков, масштабирование
   чисел, кодирование категорий.
4. Получается плотная числовая матрица + список имён столбцов; она сохраняется
   в бинарный файл для следующих работ.
5. Отклик `actual_productivity` сохраняется вместе с данными так, чтобы модели
   из Lab 2+ могли учиться предсказывать производительность.
